# 世界地图与大陆县区存档升级

## 2.1.0 海外城市足迹

海外省州边界保持不变，记录单位改为城市。`assets/geo/world-cities.json` 定义城市坐标和父省州；`world-city-migration-map.json` 仅列出已逐项核实的首府映射，来源随条目保存。现有 v3 RPC 已接受稳定的 `world:ISO3:city-<id>`，没有更改表结构、RLS、认证或保存接口。

使用 `node scripts/build-world-city-migration.mjs` 从最终冻结的公开映射和城市目录生成 `world-output/world-city-records-migration.sql`。先审查并运行 `github-source/supabase/tests/world-cities-v3.test.mjs`，再执行生成 SQL。它在同一事务内锁定当前存档并完整备份，逐字段搬移，目标已存在时保留双方；有实际变化时递增版本，以现有 CAS 拒绝旧页面的过期写入。事务结束前验证总条数、每条字段和版本，失败即整体回滚。

迁移 ID 由映射内容哈希产生，相同迁移重放不再次处理已备份账号。云端读取不再自动重复首府转换，避免用户删除城市足迹后，旧冲突记录将其重新生成。旧客户端以后新建的省州记录会显示为待整理，不能按猜测自动合并。当前网页和 Android 2.1.0 才提供城市列表与城市名称。

游客草稿优先读取 v4，缺失时回退到 v3、v2、v1。仅旧版本首次载入执行首府转换，首次保存写入独立 v4，原版本字节保持不变；当前 v4 读取不重复执行首府转换。显式导入旧版记录仍使用已核实映射，并保留目标冲突。新加坡五个分区共享一个城市 ID，多份旧记录对应同一城市时不会丢弃其他日期或笔记。

2026-10-22 已完成线上 v2 升级。迁移前完整备份，47 条记录中 45 条转到核实的政府驻地区，东莞和中山 2 条保持原位置；迁移后记录数和日期、笔记、更新时间逐字段一致。以下保留升级方法，供维护参考。

## 2.0.1 台湾与港澳层级恢复

县区细化仅限大陆（含海南）；台湾恢复22县市，港澳各为整体记录。新客户端合并政府驻地映射和 `assets/geo/region-level-reversal-map.json`。回迁仍使用管理员迁移函数，先备份每个账号的当前完整存档，再只移动映射键，不从旧备份整档覆盖。多个来源对应同一目标时保留其他完整旧键，用户可在“我的足迹”中查看或导出。

新保存入口为 `shanhe_save_archive_v3`，旧 v2 入口也返回 `CLIENT_UPDATE_REQUIRED`。请将新版网页、Android 2.0.1 和数据库版本一并发布。游客读取顺序是 v3 → v2 → v1，首次保存写 v3，旧 v2/v1 原始数据保留。

## 2.0 初始升级顺序

1. 审查 `migrations/20261022090551_shanhe_world_counties_v2.sql`。它保留既有用户读取 RLS 和 CAS 规则，开放 `shanhe_save_archive_v2`，将旧 `shanhe_save_archive` 改为返回 `CLIENT_UPDATE_REQUIRED`。此时旧 Android 1.0 和旧网页无法保存，防止它们覆盖自己无法显示的县区与海外记录。发布时需要一并提供新版网页和 APK。
2. 核实 `assets/geo/county-migration-map.json` 中每一个 `verified:true` 条目。只接受能对应到地图中真实县区的政府驻地区，并保留政府发布资料、发行文件或原始地图 POI 等可追溯来源，明确注明发布者与来源类型。多驻地或无法确认的旧记录不自动定位。
3. 从工作区根目录运行 `node scripts/build-region-data-migration.mjs`，生成 `world-output/county-records-migration.sql`。再次审查后在同一项目执行。该 SQL 不包含用户日期、笔记、邮箱或认证信息，实际迁移只在数据库内操作。
4. 检查迁移汇总和原记录字段一致性，再发布 v2 客户端。不要用真实旅行记录做增删测试。

## 数据保留

迁移管理员函数位于非公开 schema，使用 `SECURITY INVOKER`，没有给 `PUBLIC`、`anon`、`authenticated` 或 `service_role` 执行权限。它在同一个事务中锁定存档、保存完整原记录与版本、修改核实后的键并递增版本。备份表开启 RLS 且没有客户端表权限；不把私有 schema 加到 Data API 暴露列表。

已存在目的县区时，迁移保留旧城市记录和县区记录，两份日期/笔记均不合并或覆盖。映射缺失时旧键保留，由客户端待整理列表显示。相同迁移 ID 重放不产生重复操作；映射内容的 SHA-256 决定迁移 ID。备份表的 `report` 保存完整映射及逐条变更、冲突，因此可以追溯来源。恢复必须先比较当前版本和用户后续修改，不能直接整档覆盖。

客户端不改动每条记录的结构。新增 ID 支持中国六位县区码、台湾 `tw-` 加八位乡镇区码，以及 `world:ISO3` / `world:ISO3:subdivision`。仍允许旧城市码和旧台湾五位码以保留历史。最多 10,000 条、16 MiB，笔记继续限制 600 个 UTF-16 单元。浏览器实际存储配额可能更低；写入失败保留旧数据和当前输入。

游客使用 `shanhe-atlas-guest-v2`；首次读取时从旧 v1 key 载入并按核实映射转换，首次成功保存才写入 v2，原 v1 key 不变。旧客户端在本机继续修改 v1 会与 v2 分开，不会覆盖 v2。应升级所有使用中的设备。转存时同一地区存在不同日期/笔记会保留完整游客草稿，避免把未合并的旅行内容清除。
